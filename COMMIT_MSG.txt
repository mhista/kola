Give kola an answer layer; the Overview never had one

The "Ask kola" box on the Overview called KnowledgeEndpoint.searchMemory
and printed the retrieved passages verbatim. There was no model in that
path at all. What an owner saw was raw document text — literal ** and
- markers, sentences cut at a chunk boundary, the same passage twice
where a document had been saved twice.

It was honestly labelled in its own source ("deliberately NOT dressed up
as conversational AI... when the reasoning layer exists this component
gets an answer above the citations") and it still read, on screen, as a
broken AI. Reported as "the AI parsing needs work", which was the right
observation about the wrong layer: nothing was parsing because nothing
was generating.

── WHAT THE ANSWER LAYER ACTUALLY IS ────────────────────────────────

  question
    ├─ memory retrieval        the owner's own documents
    ├─ catalog digest          what they actually sell
    └─ model ──▶ tool call ──▶ { answer, product ids, intents }
                                        │
                                        └─ server resolves routes

Two constraints make this safe to put in front of an owner, and both are
about what the model is NOT allowed to do.

THE MODEL MAY POINT AT PRODUCTS, NEVER DESCRIBE THEM. It returns ids.
AnswerProducts loads those rows and renders the price, stock badge and
photo read from the database at the moment of display. A hallucinated or
stale price cannot reach the screen, because prose is never the source
of a number. The old version had the opposite property: every figure in

    - Baby Ankara wrap (Children)
      Price: ₦3,500

was a claim from an embedding made days ago, and nothing on screen
distinguished a correct one from a wrong one.

THE MODEL MAY CHOOSE AN INTENT, NEVER A URL. It picks from a closed
vocabulary; WorkspaceAnswerService maps intent → route. A model asked
for a URL will produce /inventory or /products/restock — plausible,
well-formed, not routes this app has. This codebase has already shipped
two dead links BY HAND (/settings, /catalog/:id); handing that job to
something that cannot read the router would industrialise it. All ten
intents were checked against app.dart's registered paths.

Structured output comes from a single always-called tool rather than
"return JSON", because AiOrchestrator.completeWithTools already exists
for Errands and every provider translates AiTool into its own format.
Asking for JSON means parsing whatever comes back — ```json fences
included — with no recourse when it is malformed. The fallback still
matters: a model that answers in prose instead of calling the tool
yields the prose with no products and no actions, which is degraded and
correct.

── THREE HELPERS DELETED, BECAUSE THEY WERE THE BUG ─────────────────

  _leadFor      "I found 4 places in what you have taught me..." — a
                sentence ABOUT the search, written because there was no
                answer to show.
  _noAnswerFor  the two "I don't know" variants.
  _actionsFor   keyword matching on the QUESTION. Asking "what do we
                have in the catalog" offered "Open your catalog" because
                the word "catalog" appeared — not because of anything in
                the reply.

That last one is exactly the reported complaint: actions should follow
from what was answered. It could not. There was no answer to read.

All three are removed rather than kept as a fallback. A second source of
answer text is a second thing to keep in step, and it would only ever
run when the first had already failed — which is when consistency
matters most.

── MARKDOWN: A FIXED SUBSET, CLAMPED AT BOTH ENDS ───────────────────

Paragraphs, "- " bullets, **bold**. The prompt asks for only those;
MiniMarkdown renders only those. A full CommonMark parser would render
every construct a model might emit — tables, headings, nested lists,
images, raw HTML — and each is a new way for the card to look wrong.

Tested against the cases that actually break renderers, including the
exact chunk text from the report: an unclosed ** stays literal, "2 * 3"
is not emphasis, "*roughly* 40" is not a bullet, and stray --- and
"## Sizing" are absorbed instead of printed. Bold is matched by scanning
for PAIRS, not by a regex — \*\*(.+?)\*\* mishandles all three of those.

Every leaf is Component.text, which jaspr escapes. There is no innerHTML
path. That is structural, not stylistic: this text derives from
documents the owner uploaded, and a document can contain text a customer
sent — so an HTML rendering path would make "upload this file" an XSS
vector against the owner's own dashboard.

Cards and actions wait for the stream to finish. Appearing beside a
half-written sentence makes an answer feel assembled rather than spoken.

Citations are now COLLAPSED. When the passages were the answer they had
to be open; now they are its evidence, and an owner who trusts the reply
should not scroll past its footnotes to reach the composer.

`generated: false` is on the wire deliberately. During a provider outage
the owner is told the sentence is a fallback rather than left with "kola
got worse" as the only available explanation.

── A BUG THE CSV TEMPLATE FOUND IN THE IMPORTER ─────────────────────

Running the importer's OWN canonical labels back through its matcher,
"Low-stock alert" resolved to **stock**. _fuzzy tested contains('stock')
before any low-stock rule, so a reorder threshold would have overwritten
real inventory — silently, and confidently enough to look right.

Every low-stock spelling contains "stock", so this could only be fixed
by ORDERING, never by adding more substrings. Now verified across 19
headers including variants from other systems (Reorder Level, Qty on
hand, Selling Price (NGN), low_stock_threshold).

The template itself is generated FROM csvTargetFields rather than typed
out — I typed it out first and got one label wrong, which is how the
collision surfaced. Two example rows, one stocked product and one
service with blank price and blank stock: that blank is the one thing an
owner cannot guess from a header, and typing 0 there is a false fact,
not an empty one.

── MISTAKES IN THIS CHANGE, CAUGHT BEFORE IT RAN ────────────────────

  _dedupe was an INSTANCE FIELD on a service registered as a lazy
  singleton. Product ids from one request would have silently suppressed
  the next person's — an answer missing a card for no visible reason,
  and only for the second person to ask. Now a local.

  Imported util/log.dart, which does not exist. Services use
  package:logging; `Log` is the endpoint-layer helper that takes a
  Session, and a service has none.

── STILL NOT DONE ───────────────────────────────────────────────────

Storing these interactions. A question, the passages retrieved for it,
the model that answered and whether the owner then had to correct it is
the only training corpus that would ever be trustworthy — and today
messages.body keeps the answer with none of its inputs. Deliberately not
smuggled in here: it is a retention and per-workspace-consent decision
over customer PII, and it deserves its own change. Recorded in
workspace_answer.spy.yaml's header rather than left implied.

The catalog digest is capped at 60 products. Above that the model sees a
partial list, and that fact is put IN the prompt so it qualifies its own
answer instead of describing a slice as the whole. Beyond this cap the
honest fix is retrieving the relevant subset, not sending more.

Requires: serverpod generate (two models, one endpoint).
