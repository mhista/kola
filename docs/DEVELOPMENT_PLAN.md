## Working Conventions (apply from Phase 1 onward, every phase)

These aren't a phase — they're standing rules for how code gets written throughout:

- **One component per file.** No jam-packed pages. A Jaspr screen that has a header, a form, and a list is three components in three files, composed in a fourth — not one 400-line build method. Same discipline server-side: one endpoint's business logic doesn't balloon into a single file just because it's convenient in the moment.
- **Comment in detail.** Not restating what the code obviously does, but *why* — the same way `degenbot_server`'s existing code explains rationale inline (e.g. the pubspec's package-selection-rationale block, or `REFACTOR_NOTES.md`'s explanation of the trader-rule-engine reasoning). Every service, repository, and non-obvious function gets a doc comment explaining its purpose and any constraint it's working around.
- **Deploy via `.sh` scripts**, following the pattern already proven in `degenbot_web/build.sh` and `deploy.sh`: env-var-driven (never hardcoded secrets in the script itself), a validation block that fails loudly with instructions if a required var is missing, clear emoji-flagged progress output, and a "next steps" summary printed at the end. Every deployable unit (server, web dashboard, docs site) gets its own script following this shape.
- **Reuse before rebuilding.** Before writing a service from scratch, check whether Asami or Degenbot already solved it (`SRS.md`'s tech-stack table cites the specific files to reuse — DTO/repository pattern, `IMessagingService`, `imagekit_service.dart`, payment services, wallet encryption) and whether a vetted `pub.dev` package exists before either.

## Phase 2 — Messaging Channels

**Done when:** a message sent to a real Telegram bot gets a real reply from a hardcoded/simple response, end to end through the new server.

### 2a. Telegram adapter — Done
Televerse-based `IMessagingService` implementation — this ships first because it's genuinely free and has no external approval dependency (`META_CONNECT_FLOW.md` §3a). Reuse the interface shape already proven in Degenbot/Asami.

Built as a multi-tenant registry (`kola_server/lib/src/services/messaging/telegram/telegram_bot_registry.dart`), not a single global bot like Degenbot's — every business connects their own @BotFather bot via the new `ChannelEndpoint.connectTelegramChannel`, which probes the token for real before persisting it, encrypts it at rest (`channel_credential_encryption_service.dart`, same AES-256-GCM approach as Degenbot's wallet keys), and hot-connects it with no server restart. Each connected channel gets its own webhook route (`/webhooks/telegram/<channelId>`); local dev without a public URL falls back to long-polling automatically. The bot logic itself is deliberately the hardcoded/simple reply this phase's "done when" bar asks for — Phase 3's Errand/AI orchestrator replaces it, not extends it.

### 2b. WhatsApp adapter — Done
**Revised sequencing from the original plan below, by explicit instruction:** manual connect shipped first and is the primary path, not a fallback behind Embedded Signup — Embedded Signup shares a weekly usage cap across every app using it, so a business shouldn't ever be blocked waiting on it when a manual alternative works independently of that cap and of Kola's own App Review status. See `docs/WHATSAPP_MANUAL_SETUP.md` for the full non-technical walkthrough (Meta App → System User → Standard Access token → paste into Kola) and `whatsapp_service.dart`'s header comment for why this needs no App Review dependency at all — a Cloud API token's validity is checked against its own grants, not which server calls the API.

Built the same multi-tenant shape as Telegram's registry: every connected WhatsApp channel now gets its own webhook route (`/webhooks/whatsapp/<channelId>`), same as Telegram's per-channel routes — Meta's "one App, one callback URL" limit is per-App, not platform-wide, and since Kola's manual-connect design already has each business register their own separate Meta App, each one can be handed a distinct URL. (Revised from the original design, which gave every business one shared URL and dispatched by reading `metadata.phone_number_id` out of the payload — that mechanism is kept alive as a deliberate legacy fallback for the one channel already verified against it, see `whatsapp_bot_registry.dart`'s file header.) `ChannelEndpoint.connectWhatsAppChannelManual` probes the pasted-in token/IDs against Meta for real before persisting anything, encrypts the multi-field credential at rest (same AES-256-GCM service as Telegram, JSON-encoded first), and hot-connects with no restart. Inbound messages get the same hardcoded/simple reply Telegram's Phase 2a handler gives, meeting this phase's "done when" bar for both channels.

**Original plan, kept for context, not yet built:** the in-app "Connect via Meta" Embedded Signup flow (`META_CONNECT_FLOW.md` §2) as a faster one-click alternative once it's worth the App Review investment — still has the external Meta App Review dependency the original note below describes, which is exactly why manual shipped first instead of waiting on it. **Start the Meta Tech Provider registration and App Review submission in parallel with other work whenever picked up**, not after — its timeline doesn't follow our sprint schedule.

## Phase 3 — Errand Engine & AI Orchestration

**Done when:** a bot can answer a question grounded in a manually-seeded piece of knowledge, and separately execute one built-in Errand, both through the multi-provider AI orchestrator.

### 3a. Multi-provider AI orchestrator — Done
`AiOrchestrator` (`kola_server/lib/src/services/ai/ai_orchestrator.dart`) behind a provider-agnostic `AiProvider` interface (per `SRS.md` §10) — ported from copycat/kopicat_server's `lib/ai.dart` cascade rather than reinvented, chosen for cost efficiency by explicit instruction: Groq (fast, generous free tier) tried first, Gemini next, OpenRouter's free model last, falling through to the next provider on ANY failure (bad key, quota, network error). All three are real, working implementations, not stubs — going further than the "one real, others stubbed" bar, since the whole cascade already existed and reusing all of it was cheaper than reinventing a stub. Deliberately minimal for this phase's scope (plain grounded Q&A, not yet Errand-calling) — see `ai_provider.dart`'s header for why adding tool/function-calling later is additive, not a redesign. Test via `dart run tool/test_ai_orchestrator.dart` after adding at least one API key to `.env`.

### 3b. Errand data model + built-in fulfillment — Done
`Errand`, `ErrandCredential`, `ErrandExecutionLog` models (`kola_server/lib/src/models/errand*.spy.yaml`) — Errand is workspace-scoped, not bot-scoped (SRS.md §7.3), with a dedicated `builtinHandlerKey` field (not `name`, which is free-text/owner-editable) so `BuiltinErrandExecutor` has a stable dispatch key. `ErrandExecutionLogRepository.logExecution` redacts input keys per the Errand's `sensitiveInputKeysJson` before persisting and is called unconditionally — success or failure — satisfying SRS.md §7.3's logging requirement for real. Built-in Errand type working first, before webhook/DB-credential types (`SRS.md` §7.2): `BuiltinErrandExecutor` has one real handler, `escalateToHuman` (PRD.md §6's "escalate what it can't answer"), invoked via `ErrandEndpoint.executeBuiltinErrand`. `createBuiltinErrand` deliberately only accepts `source: 'builtin'` — accepting webhook/dbCredential today would create an Errand with no way to collect its `ErrandCredential` yet.

Also closes the other half of this phase's overall "done when" bar (grounded Q&A) with a deliberately minimal mechanism, NOT SRS.md §8's real Document Parsing Engine: a plain-text `Bot.knowledgeSeed` field, injected whole into `AiOrchestrator`'s system prompt by `BotKnowledgeService.answerGrounded`. Test both via `dart run tool/test_builtin_errand.dart` and `dart run tool/test_grounded_qa.dart`.

### 3c. Webhook and database-credential Errand types — Done
Webhook-backed Errands (`webhook_errand_executor.dart`) — POSTs the Errand's input as JSON to a business-registered URL with an optional single auth header, expects a JSON result back. Database-credential Errands (`db_credential_errand_executor.dart`) — a business supplies their own Postgres connection string plus exactly one pre-approved named-parameter query template (`Errand.queryTemplateSql`, run via `package:postgres`'s `Sql.named(...)`), satisfying `SRS.md` §7.2's query-template-not-open-SQL constraint for real: there is no path from an invocation to arbitrary SQL, only named-parameter substitution into a template fixed at registration time. Read-only enforcement (default) is checked twice — once at registration (`ErrandEndpoint.createDbCredentialErrand`), once again at execution (`DbCredentialErrandExecutor`) — so editing a template later can't silently bypass the read-only guarantee without an explicit `readWrite` upgrade. MySQL (also named in `SRS.md` §7.2) is deliberately deferred, a separate driver/executor rather than a small extension of this one. Both credential shapes reuse `ChannelCredentialEncryptionService` (same AES-256-GCM service, "same pattern, different secret class" per `errand_credential.spy.yaml`'s original design note). `ErrandEndpoint.executeErrand` is the one dispatch point covering all three fulfillment types now (builtin/webhook/dbCredential) by `errand.source`. Test via `dart run tool/test_webhook_errand.dart` (self-contained, spins up its own local echo server) and `dart run tool/test_db_credential_errand.dart --connection-string=...` (needs a real Postgres URL).

### 3d. Security filter pass — Done
`SecurityFilter` (`kola_server/lib/src/services/security/security_filter.dart`) — ported from asami_server's already-prototyped `security_filter.dart` (reused, not reinvented), trimmed to drop Asami-specific vendor/customer/admin role-based tool permissions (no Kola equivalent) while keeping the generic pattern-based detectors: prompt injection, SQL injection, XSS, credential leakage, phishing, spam/repetition, rate limiting. Three checkpoints matching `SRS.md` §10's three trigger moments: `checkInboundMessage` (wired into `InboundMessageHandler`, before any customer message reaches the AI orchestrator), `checkErrandInput` (wired into `ErrandEndpoint`'s execute methods, before any Errand fulfillment call — builtin/webhook/dbCredential alike), `checkOutboundText` (wired into `InboundMessageHandler`, on the AI's own drafted reply before it's sent — a blocked reply escalates to a human rather than being silently substituted). Deliberately the MVP guardrail, not the fraud engine itself — plain pattern matching, same as Asami's prototype — this is the seam the Phase 3-of-the-*product*-roadmap fraud engine plugs into later, not a replacement for it. Test via `dart run tool/test_security_filter.dart`.

### 3e. Escalation feature: Conversation/Message + owner notifications — Done
Introduced mid-Phase-3 by explicit product direction, built as the full loop in one pass rather than staged: `Conversation`/`Message` models (`kola_server/lib/src/models/{conversation,message}.spy.yaml`, SRS.md §6) with a `bot` → `escalated` → `closed` state machine; `InboundMessageHandler` (`kola_server/lib/src/services/conversations/inbound_message_handler.dart`) shared by both `TelegramBotRegistry` and `WhatsAppBotRegistry`, replacing their Phase 2 hardcoded canned replies entirely — every inbound text now persists to a Conversation/Message trail and gets a real grounded answer from `BotKnowledgeService`.

Escalation trigger was originally a deliberate stand-in for real AI tool-calling: the model was instructed to end its answer with a plain sentinel token when it can't help, which `BotKnowledgeService.answerGrounded` parsed into a `needsEscalation` flag. Real tool-calling shipped in 3f below — `InboundMessageHandler` now calls `BotKnowledgeService.decide()` instead, and escalation is just the model calling a reserved tool like any other. `answerGrounded`/the sentinel token are unchanged, for any other caller that still wants plain grounded Q&A without Errand-calling.

Owner notifications fan out via `OwnerNotificationDispatcher` (`kola_server/lib/src/services/notifications/`) to WhatsApp (sent from the workspace's own connected channel), a separate Kola-owned long-polling Telegram bot (`kola_notifier_bot.dart`), and email (`package:mailer`, same technique as `asami_server`) — WhatsApp and email rate-limited per plan tier since Meta bills per WhatsApp conversation (`NotificationRateLimiter`: free/pro/business daily caps), Telegram uncapped, SMS an explicit architectural placeholder only (`sms_owner_notifier.dart` — every interface/model slot exists, no provider wired in yet, per instruction to "bake in the architecture" without implementing it).

`ConversationEndpoint` (`kola_server/lib/src/endpoints/conversation_endpoint.dart`) is the bare-bones inbox surface — `listEscalated`, `getMessages`, `sendHumanReply` (persists AND actually sends via the right platform registry), `closeConversation` — deliberately not the full Phase 4 dashboard UI, which still doesn't exist for this feature (matches "Kola Conversations.dc.html"'s design conceptually, doesn't render it yet). Migration `006_conversations_and_notifications.sql` covers all four new tables.

### 3f. AI tool-calling Errand engine — Done
The real thing `ai_provider.dart`'s original header promised was additive, not a redesign: `AiProvider.completeWithTools()` sits alongside `complete()` (untouched) on all three providers — OpenAI-compatible `tools`/`tool_calls` for Groq/OpenRouter, Gemini's own `functionDeclarations`/`functionCall` shape for Gemini — with `AiOrchestrator.completeWithTools()` cascading across them the same way `complete()` already did. `errand_tool_registry.dart` converts a workspace's active Errands into that call's `tools` list (builtin handlers get a hand-written JSON Schema per handler key; webhook/dbCredential Errands get one converted from their flat `inputSchemaJson`), plus a reserved, always-available `escalate_to_human` tool that isn't tied to any Errand row — escalation is a platform guarantee, not something a business could forget to configure. `BotKnowledgeService.decide()` is the tool-aware sibling of `answerGrounded()` (that method is untouched). `ErrandDispatchService` extracts `ErrandEndpoint.executeErrand`'s dispatch-by-source switch into a Session-free service so `InboundMessageHandler` can invoke any Errand type the AI chooses — after merging in context the model was never asked to supply (e.g. `conversationId`) and running `SecurityFilter.checkErrandInput` on the AI-inferred arguments, same "before ANY Errand call" rule as the human/API-triggered path. A builtin handler's own `replyToCustomer` becomes the reply directly; a webhook/dbCredential Errand's raw JSON result is summarized into plain language by a second, tool-free AI call (`BotKnowledgeService.summarizeToolResult`). `ErrandEndpoint.deleteErrand` also shipped alongside this (owner request: disabled Errands should be deletable) — requires `status == 'disabled'` first.

## Phase 4 — Dashboard (Jaspr + Relic)

**Unblocked:** the Kola design system specs (12 `.dc.html` page exports) and a confirmed real Jaspr+Relic reference pattern (`copycat`/`kopicat`) are both in hand. More Jaspr reference project links may still arrive and should be reviewed as they do, but there's now enough to start.

### 4a. Confirmed Jaspr + Relic pattern
Every real precedent examined so far — `degenbot_web`, `kopicat` (root), `kopicat_landing` — uses **`jaspr: mode: client`** (static/compiled-JS), not server-rendered Jaspr. Relic shows up specifically on the **server** side in `kopicat_server`: a standalone `RelicApp()` with chained `.get`/`.post` route registration and a `.fallback`, one `Handler get xHandler => (Request req) async {...}` per file under `lib/routes/`, `Response.badRequest`/`.internalServerError` for error paths, `Body.fromString(jsonEncode(...), mimeType: MimeType.json)` for JSON responses. Applied to Kola: **the dashboard is a `jaspr: mode: client` app that calls our own Serverpod-fronted API — with a Relic-based thin API layer only if/where we need a lightweight HTTP surface Serverpod's generated client doesn't already cover** (e.g. webhook receivers, file upload endpoints). This is a deliberate, confirmed choice, not a guess — but it does leave one open question worth a conscious decision rather than a silent default: `SRS.md`'s original assumption of an SSR-first marketing/dashboard site (for SEO) conflicts with every real precedent being client-mode. Recommendation: client-mode for the dashboard (no SEO need, matches every reference project) and client-mode for the landing/marketing/docs surfaces too unless SEO performance data later says otherwise — flagged in `SRS.md` §3 as a decision made, with the tradeoff stated, not an unresolved gap.

### 4b. Confirm remaining Relic/Jaspr reference projects as they're shared
Read each new linked reference project before writing dashboard code that depends on its pattern — this is exactly the mistake the "don't guess at architecture" principle throughout this project has been avoiding.

### 4e. Real auth + Errand builder + Knowledge base — Done (Conversations/Integrations still pending)
Two genuine architecture questions surfaced and were resolved before writing any page code, both confirmed against the actual generated code rather than assumed: (1) the dashboard talks to `kola_server` exclusively through `kola_client` (Serverpod's generated RPC client) — never direct DB access, never a bespoke Relic/REST layer, matching Phase 4a's original decision; (2) `serverpod_client`'s pub.dev listing confirms "web" as a supported platform with no `dart:io`-only dependencies, so `dart compile js`-compiling `kola_client` into this Jaspr client-mode app is safe — verified, not assumed.

Two scope decisions were put to the project owner directly (via explicit prompt, not decided unilaterally) once real gaps were found: no auth flow existed anywhere in `kola_dashboard`, and the Knowledge Base page's design promises file upload/parsing that `kola_server` never built (the only real knowledge storage is `Bot.knowledgeSeed`, a single plain-text field). Both were resolved with the recommended, smaller-scope option: **build a real Supabase Auth flow now**, and **ship a minimal textarea page for Knowledge now** rather than a file-upload UI pointing at nothing.

**Auth**: `kola_server` verifies Supabase JWTs locally (HS256 against `SUPABASE_JWT_SECRET`) and has no login/signup endpoint of its own, so `kola_dashboard` talks directly to Supabase Auth's REST API (`/auth/v1/signup`, `/auth/v1/token?grant_type=password`, `?grant_type=refresh_token`) via plain `http` calls — not the `supabase` package, whose ~9 transitive dependencies (realtime/storage/postgrest/functions/rxdart) are unneeded for sign-in/sign-up/refresh alone. Same "raw HTTP over a heavy client library" choice `kola_landing` already made for its waitlist form. New: `services/auth_service.dart`, `services/local_storage.dart` (`package:web`, not `dart:html`), `models/auth_session.dart`, `pages/login_page.dart`, `pages/create_workspace_page.dart` (the real first-write path — see `WorkspaceEndpoint.createWorkspace`'s own doc comment).

**`kola_dashboard/pubspec.yaml`** joined the repo's Dart pub workspace (added `resolution: workspace`, bumped `sdk: ^3.8.0`) so it could path-depend on `../kola_client`, the same requirement `kola_flutter` already satisfies.

**`lib/app.dart`** is now a `StatefulComponent` (was `StatelessComponent` in 4d) holding the live `Client`, `AuthSession?`, and selected `Workspace?` — needed because `jaspr_router`'s `Route` builders now close over live session/workspace state, not just URL params. A single `redirect` callback on the root `Router` (jaspr_router's `RouterRedirect`) is the one place access is gated: unauthenticated → `/login`; authenticated but workspace-less → `/create-workspace`; otherwise proceed. `DashboardHomePage`/`BotDetailChatPage`/`BotDetailDevPage` deliberately stay on Phase 4c/4d's mock data this phase — rewiring those three to real data was not needed to unblock Errand Builder/Knowledge, which only ever needed `accessToken` + `workspaceId`.

**Errand builder** (`pages/errand_builder_page.dart`, real route `/errands`): scoped to exactly what `EndpointErrand` supports today — creating a **built-in** Errand (`createBuiltinErrand`, hardcoded to the only registered handler, `escalateToHuman`) plus listing and enabling/disabling existing ones. Deliberately does not offer DB-query or webhook Errand creation — those need a DB credential / webhook secret this dashboard has no UI for yet, and building a form that promises them without a working backend flow would repeat the exact "Knowledge Base promises document parsing that doesn't exist" gap that got descoped this same phase. Errands are scoped to a workspace, not a bot (confirmed against `EndpointErrand`'s method signatures — none take a `botId`), so no bot selector was built.

**Knowledge base** (`pages/knowledge_page.dart`, real route `/knowledge`): per the project owner's chosen scope — a bot picker plus one textarea bound to that bot's `knowledgeSeed`, saved via `EndpointBot.setKnowledgeSeed`. No file upload UI, on purpose.

`sidebar_nav.dart`'s Errands/Knowledge nav items and the two matching home-page quick actions now point at these real routes instead of `#`; `quick_actions_grid.dart`/`quick_actions_list.dart` gained the same `#`-vs-real-route → plain-anchor-vs-`Link` branching `sidebar_nav.dart` already had, so the new routes get client-side navigation instead of a full page reload.

### 8a. Live payment collection Errand — Done
PRD.md §7: "Live payment collection Errand (Paystack/Flutterwave) with escrow-style hold option (informed by Asami's `order_escrow` pattern)." **Buildable now.**

Before writing any code, checked how Asami actually implements escrow (`asami_server/lib/src/models/order/order_escrow.spy.yaml`, `.../services/wallet/escrow_automation_service.dart`) rather than guessing from the PRD's one-line mention. Asami's version is a full marketplace wallet ledger — orders, vendor wallets, a platform-fee split, a delivery-deadline/return-window state machine — because Asami itself is the merchant of record, collecting into its own Paystack account and later disbursing to vendors via Transfer API calls. **That model does not fit Kola:** Kola is bot-as-a-service, not a marketplace, and PRD.md §8's own "we store the least we can" principle plus the BYO-credential pattern already used for every other integration in this codebase (Telegram bot token, WhatsApp access token, webhook URL, database connection string — every one supplied and encrypted per-workspace, never a Kola-wide shared secret standing in for a business's own account) argue against Kola ever becoming a payment custodian. Becoming one the way Asami is would mean Transfer/Recipient API integration, KYC obligations, and real regulatory exposure — a business decision, not an engineering default to reach for.

So this phase builds the BYO version: each workspace connects **its own** Paystack and/or Flutterwave secret key (same probe-before-persist, encrypt-at-rest pattern as `ChannelEndpoint.connectTelegramChannel`), and a checkout initializes against that workspace's own account — money goes straight to the business, the same way it always has, with Kola never touching it. The "escrow-style hold option" is carried over as a bookkeeping status flag only (`held`/`released`, e.g. "don't tell the vendor to ship until this is released"), not real fund custody — flagged explicitly in code, since claiming otherwise would be the same kind of overstatement this project has caught and corrected elsewhere (`WHATSAPP_MANUAL_SETUP.md`'s credential-health-check claim, task #85's docs corrections).

**Built:** `PaymentGatewayCredential` + `PaymentTransaction` models (migration `009_payment_transactions.sql`); `PaymentEndpoint` (`connectGateway` — probes a real, cheap authenticated call before persisting, same as every other BYO-credential connect flow in this codebase; `initializeCheckout`; `getTransaction`; `releaseHold`); `PaymentWebhookHandler` + one shared route per gateway (`/webhooks/paystack`, `/webhooks/flutterwave` — one route total per gateway across every workspace, not per-workspace, since each business's own gateway dashboard is where their webhook URL is configured; dispatch happens by looking up the payload's own reference to find the right workspace's stored credential to verify against — see that file's header for why this is safe, not a hole). Flutterwave connections additionally need a webhook secret hash (separate from the API secret key — see `payment_gateway_credential.spy.yaml`).

**Task #128 (done, same day):** a `collectPayment` handler is now wired into `BuiltinErrandExecutor` — a bot can trigger a real checkout mid-conversation, not just via `PaymentEndpoint`'s direct API surface. This meant extracting the actual checkout logic out of `PaymentEndpoint.initializeCheckout` into a new caller-agnostic `PaymentCheckoutService` (no Session/accessToken — an AI-orchestrated bot's context never had one to check), and changing `BuiltinErrandHandler`'s typedef so every handler now receives the owning `Errand` (for `errand.workspaceId`), not just `input` — a mechanical signature change for the pre-existing `escalateToHuman` handler, not a behavior change.

### 8m. The Connect Gate — connector-native agent capabilities, gated on connection alone, no Errand row required — Done, and entirely undocumented here until this correction (2026-08-31)

Found while auditing 8a for staleness: `connector_capability_registry.dart` (a real, fully-wired file — `ConnectorCapabilityRegistry` is DI-registered and injected into `InboundMessageHandler`, called on every inbound message right alongside `ErrandRepository.listActiveByWorkspace`) implements something neither this document nor 8a's stale note ever mentioned.

**The bug this closes, in the file's own words:** before this existed, `'collectPayment'` and `'bookCalendarEvent'` only became callable tools for the AI orchestrator if a business had ALSO gone and manually registered a matching `Errand` row — so a business could connect Paystack under Integrations and still have an agent unable to take a payment, because nobody separately created the Errand. **The fix:** connecting the underlying connector IS the configuration step now; there is no second one to skip. `ConnectorCapabilityRegistry.forWorkspace` builds synthetic, never-persisted `Errand` objects on the fly — one per capability the workspace currently has connected — using small fixed **negative** ids (`SyntheticErrandIds.collectPayment = -1`, `.bookCalendarEvent = -2`, `.checkRecentTransactions = -3`) that can never collide with a real Errand's positive serial primary key, and hands them to the exact same `ErrandToolRegistry`/`ErrandDispatchService` machinery real Errands already go through — zero new dispatch code, same pattern `errand_tool_registry.dart`'s pre-existing `escalate_to_human` platform-wide capability already proved, just per-connector instead of platform-wide.

**Three capabilities live today:**
- `collectPayment` — appears the moment `PaymentGatewayCredentialRepository.listByWorkspace` returns any row (Paystack and/or Flutterwave connected, from 8a above).
- `checkRecentTransactions` — added alongside it, same gate. Found 2026-08-24 as a real, separate gap: `WorkspaceAnswerService` (the owner-dashboard assistant) could tell an owner "Paystack: connected" but had no tool to actually look up a transaction, so "check my paystack transaction" read as a refusal with no path to the data. Read-only, backed directly by `PaymentTransactionRepository` (Kola's own synced record, not a live gateway API call).
- `bookCalendarEvent` — appears once a `google_calendar` `WorkspaceConnector` row exists with `status == 'connected'`. Backed by a real, separate build: `GoogleOAuthService`-based OAuth connect (`ConnectorEndpoint`, reusing the same OAuth machinery as Drive/HubSpot/Dropbox, scoped to `GoogleOAuthService.scopeCalendarEvents`), a `CalendarBookingService` with a genuinely two-mode design (`draft` — writes a `pending` row, touches nothing in Google, the safe default for an unset workspace — versus `immediate` — books directly against Google Calendar right away), and a per-workspace `setCalendarBookingMode` setting stored in the same encrypted OAuth config blob rather than a new column, since the mode isn't itself secret, it just configures the connection it lives beside. Dashboard-wired: `integrations_page.dart` has the connect flow and the booking-mode toggle.

**Why this belongs in the plan, not just in the code:** this is a real architectural pattern (gate agent capability on connection state, not on a manually-registered Errand) that will keep applying to whatever connector Kola adds next — worth knowing exists before reaching for the older "add an Errand template" pattern out of habit.

### 8k. Messenger and Instagram DM channels — both built and live (2026-08-30/31, see below)

Lower-intent, high-frequency chat (browsing questions rather than a closing conversation) is the best candidate to move there.

## Phase 9 — Layer 2: Business Memory

**The AI-OS restructure starts here.** The project brief describes Kola as a ten-layer AI Operating System for SMEs. Measured against that, what existed after Phase 8 was a very capable multi-tenant AI bot platform: the model layer was ~80% there (a real three-provider cascade with real tool-calling), multi-tenancy ~85%, interfaces ~40%. **Business Memory was ~15%, and Layers 4–9 (Event Bus, Observation, Recommendation, Timeline, Continuous Learning) were at zero.**

**STALENESS CORRECTION (2026-08-31):** "were at zero" stopped being true not long after this was written, and the doc was never updated — Layers 4 (Event Bus) and 5/6 (Observation/Recommendation) are now both real and shipped, entirely undocumented anywhere in this file until this correction. See the new **Phase 12** section below, added at the same time as this note.

Memory goes first, and not arbitrarily: the Observation, Recommendation, Timeline and Continuous-Learning layers are all *readers* of memory and events. Building any of them on top of `Bot.knowledgeSeed` — a single 2,000-character plain-text field pasted whole into the system prompt — would mean rebuilding them the moment real memory landed. This is the load-bearing layer, so it is the one that gets built first.

**Done when:** a business can store real documents, a bot answers from semantically-retrieved passages rather than one text blob, and every answer can name the specific document and section it came from.

### 9a. Embedding provider — Done

`EmbeddingProvider` / `GeminiEmbeddingProvider` / `EmbeddingOrchestrator` (`kola_server/lib/src/services/memory/`), mirroring `AiProvider`/`AiOrchestrator`'s shape so this is the same pattern rather than a new one.

**Deliberately a separate interface from `AiProvider`, not a new method on it.** Of the three providers already in the cascade, only Gemini can produce embeddings at all — Groq serves inference models only and has no embeddings endpoint, and OpenRouter does not proxy embeddings. Adding `embed()` to `AiProvider` would have forced two of three implementations into permanent `UnsupportedError` stubs and made the "fall through on any failure" cascade meaningless for embeddings.

**And it is deliberately NOT a failover cascade.** `AiOrchestrator` falls through to the next provider on any error, which is right for chat because any provider can answer the same question. It would be actively harmful here: vectors from two different models are points in unrelated spaces, so falling back mid-ingestion would silently write chunks that a query embedded by the first provider can never retrieve. That failure surfaces months later as "the bot suddenly can't find things," not as an error. So `EmbeddingOrchestrator` picks the first configured provider **once** and surfaces quota errors to the caller instead of switching model families. `knowledge_chunks.embedding_model` records which model produced each row so a future provider change is a findable, migratable data problem rather than silent corruption.

**768 dimensions, not `gemini-embedding-001`'s 3072 default.** Three concrete reasons, in order of how binding they are: pgvector's HNSW index caps at 2000 dimensions, so 3072 could be stored but never indexed — every search would sequentially scan the table; storage is 3KB/chunk instead of 12.3KB; and the model is trained with Matryoshka Representation Learning, so 768 is one of Google's own recommended truncation points rather than a naive slice. Truncated MRL vectors are **not** unit-length even though the full 3072 output is, so the provider re-normalizes rather than trusting a guarantee made at a different length — not doing so is a silent, hard-to-trace quality bug.

**Zero additional cost, deliberately.** Uses the same `GEMINI_API_KEY` the chat-side provider already uses — no new credential, no new vendor relationship, and `gemini-embedding-001` has a real free tier (1,500 requests/day). With no key set, every service degrades gracefully rather than failing: ingestion reports `unavailable`, retrieval returns empty, and `BotKnowledgeService` falls straight back to `knowledgeSeed`. Nothing in this phase can begin billing on its own.

### 9b. Models, schema, and the similarity RPC — Done

`KnowledgeDocument` + `KnowledgeChunk` (`.spy.yaml`, DTOs, repositories per the established `BaseDto` pattern) and `docs/migrations/017_business_memory.sql`.

**Workspace-scoped, not bot-scoped** — the single most consequential decision in the model. A business's return policy is a fact about the business; if a workspace runs a customer-care bot and a catalog bot, both should know it, and the owner should not maintain two copies. This follows the precedent Errands already set, and it is what makes the specialized-agent architecture (Sales/Finance/HR agents sharing one memory) possible later. Bot-scoping now would have to be undone then.

**The embedding vector is deliberately not a model field.** Serverpod can model a `List<double>`, so this was a real choice: as a field it would be serialized to the dashboard on every call (~3KB of unusable noise per chunk), Postgres's `vector` type has no Serverpod equivalent so it would round-trip through JSON and lose the typed column the index depends on, and similarity search can't go through PostgREST anyway. The repository owns the vector column; the model describes the readable chunk.

**Retrieval goes through a `match_knowledge_chunks` SQL function, not a PostgREST query** — vector distance ordering cannot be expressed in PostgREST's filter syntax at all. This is Supabase's own documented pgvector pattern, not a workaround. Tenant isolation is applied *inside* the same query as the vector scan rather than by joining out to the parent document, so the similarity scan never runs ahead of the tenant filter.

**One migration detail worth stating, because getting it wrong is silent:** the migration sets an explicit `search_path` and references `vector` unqualified rather than as `extensions.vector`. If a project enabled pgvector earlier and it lives in `public`, `create extension if not exists ... with schema extensions` does nothing and every schema-qualified reference then fails. The function pins its own `search_path` too, since a function resolves that at execution time from the caller's session, not from the migration that created it.

### 9c. Ingestion and chunking — Done

`TextChunker` and `DocumentIngestionService`.

**The order of operations is the design.** Hash and dedupe *first* (embedding is the only step that costs quota, so checking whether we already have this text before embedding it is the entire reason a content hash is stored). Persist the document as `pending` *before* embedding, so a failure has a real row to attach a reason to and the owner sees "failed: quota exceeded" rather than an upload silently vanishing. Mark `indexed` *last* — `match_knowledge_chunks` ignores anything not `indexed`, so a crash mid-ingestion leaves a document invisible rather than half-answerable. **A silently-failed document is the worst outcome in this subsystem**, because the owner then believes the bot was told something it was never told.

**Chunking is where answer quality is actually decided** — retrieval can only ever return whole chunks. The strategy escalates paragraph → sentence → word boundary, with overlap so a fact straddling a boundary appears whole somewhere. It is explicitly a v1 and not structure-aware: markdown headings and tables are just short paragraphs to it. That's a real limitation, and improving it should be done against real business documents rather than guessed at now.

**File parsing — STALENESS CORRECTION (2026-08-31): narrower gap now than described here.** This originally said file parsing was not built at all. Since then (Gate 6), `xlsx_extractor.dart` genuinely parses `.xlsx`/`.xlsm`, and `.csv`/`.tsv` go through a real preamble-wrapped text extraction — both feed `KnowledgeEndpoint.addDocumentFromFile` into the same `ingestText` contract this section describes, unchanged. Only PDF and DOCX are still explicitly refused with an honest "cannot read yet" message rather than attempting something that would produce garbage chunks — the original reasoning below still holds for exactly those two formats: parsing them properly means vetting packages per format and handling scanned-image PDFs that need OCR, and extracting whatever bytes look like text would produce chunks that embed to noise and surface as confidently wrong answers, strictly worse than refusing the file. Extraction for those two still belongs in a separate service feeding `ingestText` whenever it arrives.

### 9d. Retrieval, citations, and the rewire — Done

`MemoryRetrievalService` + `KnowledgeEndpoint`, and `BotKnowledgeService` rewired.

**This is where "every AI answer must cite where its information came from" stops being aspirational.** Retrieved passages are numbered and labelled with their source document, and `GroundedAnswer.citations` / `KnowledgeDecision.citations` carry those sources back to the caller — so an answer is traceable to a specific document and section rather than the bot being trusted on faith. Without it, grounded retrieval is just a fancier way to stuff text into a prompt.

**`answerGrounded` and `decide` kept their exact signatures and contracts** — only the *source* of the `--- BUSINESS INFORMATION ---` block changed. That is precisely what `bot_knowledge_service.dart`'s original Phase 3b header predicted would happen ("real retrieval replaces reading that field directly here; this file's job stays the same shape, just fed by a smarter source").

**The `knowledgeSeed` fallback is deliberate and not temporary-until-we-get-around-to-it**, for three real reasons: every existing workspace has content in `knowledgeSeed` and none in `knowledge_documents`, so cutting over without it would make every live bot instantly stop knowing anything; a key-less deployment has no embeddings and degrading is better than refusing to answer; and a small seed ("we're a fashion store in Lagos, open 9–6") is genuinely useful context no retrieval hit would surface. **Migration 017 therefore does not drop the column**, and it shouldn't be dropped until every workspace has migrated across.

**A similarity floor is set deliberately (0.35), not left at zero.** Without a floor every query returns its nearest six chunks no matter how irrelevant, and the model dutifully answers from them — which is how a grounded bot starts confidently misciting a price list to answer a delivery question. Chunks are then taken in similarity order until a token budget is spent, rather than a fixed top-N, so a query matching six long chunks can't silently overflow the context window and get truncated from the end (where the conversation lives).

`KnowledgeEndpoint` is a new endpoint rather than more methods on `BotEndpoint`, because knowledge is no longer a property of one bot and hanging workspace-scoped memory off a bot-scoped endpoint would encode the wrong ownership model in the API. `BotEndpoint.setKnowledgeSeed` is left alone and still works. `searchMemory` returns real scored hits — an owner can type a question a customer actually asked and see exactly which passages ground the answer, which turns "the AI got that wrong" from an unfalsifiable complaint into something inspectable.

## Phase 10 — Release Control & the Admin Control Plane

**Introduced by explicit product direction, and it changes how everything after it ships.** The instruction, in the owner's words: *"we won't release everything so as not to overwhelm users, we'll programmatically lock certain features, and only unlock them in phases and when needed... it will be seamless releases, in a way that each release complements the other."*

**The principle: decouple BUILD from RELEASE.** A feature ships to production `locked` — fully built, fully running, entirely invisible — and is later flipped to `beta` for chosen workspaces, then `released` for everyone. **Unlocking is a database state change made from kola_admin. No deploy, no downtime, no code change.**

This resolves a real tension. Build velocity is now constrained by engineering capacity, which with AI assistance is fast. Release velocity is constrained by user absorption and support capacity, which is not. Forcing them to move together wastes the first or breaks the second.

**Done when:** every gateable capability has a flag, resolution is centralised in one service with one precedence order, and a feature can be unlocked without a deployment. — satisfied.

### 10a. The feature registry and resolver — Done

`FeatureKeys` (`kola_server/lib/src/services/features/feature_keys.dart`) declares **49 capabilities** across seven release waves. `FeatureFlagService` is the one place that answers "can this workspace see this feature."

**Which features exist is defined in Dart; what state each one is in is defined in the database.** That split is deliberate and load-bearing: feature keys are referenced in code (`requireFeature(FeatureKeys.observations)`), so a key existing only in a database row would let a typo compile fine and then silently resolve to "unknown feature" → fail-closed → disabled. **A shipped feature nobody can see, and nobody knows is missing, is the worst outcome this system can produce.** `FeatureFlagService.reconcile()` reports drift in both directions and kola_admin surfaces it on load.

**Four states, not a boolean** — `locked` / `internal` / `beta` / `released` — because "built" and "released" are different events with observable steps between them. **`beta` is per-workspace opt-in rather than a percentage rollout**: with a customer base this size a percentage is meaningless and untraceable, while knowing exactly which four businesses have a feature — and being able to call them — is worth far more.

**Resolution order, defined in exactly one place** (`feature_flag_service.dart`'s header, and nowhere else): unknown key → false, logged at severe · explicit disable always wins, even over `released` · externally-gated features cannot be switched on early by any override · explicit enable wins for everything else · then platform state · then minimum plan, checked **last and only for released features** (a design partner on the free tier is still a design partner).

**`minimumPlan` is deliberately a separate field from `state`**, because they answer different questions — "has this shipped" versus "do we charge for it". Collapsing them would make it impossible to run a paid feature in beta, which is exactly what a design-partner programme has to do. It reads `TrialStateMachine.effectiveTier`, not `Workspace.plan` directly, so a workspace inside its 48-hour full trial sees paid features and a lapsed one does not — reading `.plan` would have silently bypassed the entire trial mechanic.

**Caching, and why the TTL is short.** `isEnabled` sits on the inbound-message path; uncached it would add two database round trips to every customer WhatsApp message. TTL is **30 seconds** rather than something more efficient because this system's most urgent operation is the kill switch — flipping a broken feature to `locked` at 2am must take effect in seconds. `invalidate()` exists so an admin action takes effect immediately rather than waiting out even that. **A database failure serves stale rather than failing**, because returning an empty map would — given fail-closed resolution — turn every feature off across the platform.

### 10b. Schema and seed — Done, applied and verified

Migration `018_feature_flags.sql`: `feature_flags`, `workspace_feature_overrides`, and `workspaces.is_internal`. **Applied to the live `kola` project and verified behaviourally.**

**Two guarantees the schema enforces, both tested against the live database:**

1. **Re-running the seed can never re-lock a released feature.** The `on conflict (key) do update` clause refreshes name, description, plan, phase and gating — but deliberately never `state`. Verified: `timeline.core` was flipped to `released`, the seed re-run exactly as a later deploy would, and it stayed `released`.
2. **Every override must carry a written reason.** `note` is `NOT NULL`. An unexplained override found six months later cannot be safely removed, so the schema refuses to create one.

Also verified: an override referencing an unknown feature key is rejected (FK) · a duplicate override for the same workspace+feature is rejected (unique constraint, since two would make resolution ambiguous) · invalid `state` and `release_phase` values are rejected (check constraints). Final state: **49 flags, 11 released (all R1), 38 locked, 0 overrides, 0 internal workspaces.**

A customer-reachable path that could mint an internal workspace would unlock every unreleased feature on the platform and make this entire system decorative.

### 10c. Customer-facing read surface — Done

`FeatureEndpoint` — **read-only, completely and deliberately.** No method changes a flag or creates an override; all of that lives in kola_admin behind separate auth in a separate deployable.

`listEnabledFeatures` returns a list rather than offering per-feature checks, because the dashboard needs to know what to render *before* it renders — which nav items exist, which routes resolve. Per-component checks would be dozens of round trips to build one page.

**Only ENABLED keys are returned.** A locked feature is absent from the response entirely, not present with `false` — the locked set is an unreleased product roadmap, and a customer inspecting network traffic should not be able to read it.

### 10d. Release waves — Decided, documented in `docs/RELEASE_PHASES.md`

Seven waves, sequenced by **"what does this unlock make true that wasn't true before"** rather than "what happens to be finished":

**R1 Foundation** (11, released today) — *it answers your customers, from what you taught it* · **R2 Visibility** (6) — *it remembers, and now shows you* · **R3 Intelligence** (5) — *it noticed something you hadn't* · **R4 Delegation** (8) — *it acts, with your approval* · **R5 Reach** (9) — *wherever your customers are* · **R6 Platform** (5) — *build on it* · **R7 Enterprise** (5) — *at scale, safely*.

**Three sequencing decisions worth recording:**

- **`platform.event_bus` leads R2**, and shipping it locked-but-running is the point: it starts accumulating history immediately, so by the time Observations unlocks in R3 there are months of real events to observe rather than an empty table. An observation engine switched on against two weeks of data produces nothing useful.
- **R3 gets the slowest rollout on the roadmap** — internal, then three to five named design partners, then general — because these features are cheap to build and expensive to *tune*. "Is a 30% dip worth flagging?" cannot be answered from first principles. And the cost of error is asymmetric: an owner told sales dropped when they didn't stops trusting every subsequent observation, including the correct ones. **Trust here is spent once.**
- **`errands.webhook` and `errands.db_credential` are locked in R6 despite having shipped in Phase 3c.** They are finished. They are held because they are developer-facing capabilities that need the Developer Portal to be supportable — releasing a database-query errand with no documentation, key management or delivery logs would generate support load out of all proportion to adoption.

**Three R5 features and two R7 features are marked `externally_gated`** — Messenger, Instagram and broadcast wait on Meta App Review; SSO and data residency wait on an auditor and legal artefacts. **No override can switch these on early**, which prevents an admin enabling something for a prospect that Meta or a procurement review will then reject. **This is also the honest correction to the alignment check's "3 years" figure:** that was never about build time. SOC 2 Type II needs an observation window with a real auditor; HIPAA needs a signed BAA. Those are calendar-bound and legal, and AI does not compress them.

**No dates.** Every unlock trigger is a condition, not a calendar entry — attaching dates to conditions that depend on real usage would be inventing certainty.

### 10e. `kola_admin` — Built and live (staleness-corrected 2026-08-31; this section sat marked "specified, not yet built" for a long stretch after the app had actually shipped — the same class of documentation-drift error 8k's and Phase 11's own staleness corrections warn about)

Full specification in `docs/ADMIN_APP_SPEC.md`. **Confirmed with the owner as a separate application**, not a role-gated section of `kola_dashboard`.

**The deciding argument is security blast radius.** If admin routes live inside `kola_dashboard`, every control surface and endpoint name ships in the JavaScript bundle downloaded by every customer, and the only thing between a customer and platform-wide feature control is a role check in code they hold a copy of. A bug in customer-facing code affects one workspace; a bug in the boundary around admin code affects every workspace, the unreleased roadmap, and every customer's data. Secondary but real: admin needs its own auth with mandatory MFA (wrong to impose on every SME owner), a different deploy cadence, and a different design target (a dense keyboard-driven operator surface versus a shop owner on a phone).

## Phase 11 — Commerce (Catalog, Point of Sale, Offline, Documents) — Core till, all four customer-facing surfaces, and offline sync all built; second-tier catalog surfaces (photo/voice entry, non-packaged-goods archetypes) still open

**STALENESS CORRECTION (2026-08-30):** this phase sat marked "specified, not built" for a long stretch after real commerce work had already shipped — the exact failure this document's own Phase 9 section warns about elsewhere ("an audit updated only when someone remembers is an audit that is accurate exactly when it is least needed"). Corrected here rather than left to mislead the next reader.

**Introduced by explicit product direction. Ships in V1, optional per business.** Full design brief in `docs/DESIGN_BRIEF_COMMERCE.md`.

**The framing that decides everything else:** this is not a POS module bolted onto an AI product. **It is the sensor.** Every scan says what sold, at what price, at what time, alongside what — a shop running a till for one week has told Kola more about itself than a month of document uploads. Memory (Phase 9) and the Event Bus (Phase 12) are the layers everything reads from; commerce is what fills them.

If it were a standalone POS it would compete with Square and Loyverse on feature count and lose. It is not competing with them — **it is the only till that makes the business's AI smarter every time it rings up a sale.**

**Two things nothing else does:** the catalog IS memory, so a customer asking on WhatsApp *"do you have red ankara size 12?"* gets an answer from live stock at the real price — the bot and the till read the same thing. And the receipt is a relationship rather than a slip: warranty, return window, reorder link, attached to the customer profile.

### Confirmed scope decisions

- **Offline selling with sync**, not read-only. A shop that cannot sell during an outage keeps a paper book beside the product, and the moment they do Kola stops being the system of record. Sales, receipts and stock changes queue locally and reconcile on reconnect, with stock conflict resolution expressed in plain language — never a merge-conflict UI shown to a shop owner.
- **Web PWA on whatever the business already owns** — phone, cheap Android tablet, or laptop. Camera as barcode scanner, browser printing. No hardware purchase, no app store.
- **All four customer-facing surfaces**: catalog through the bot, a shareable public catalog page, an owner-configurable in-store customer display, and a digital receipt delivered to WhatsApp. All printable and shareable.
- **Product archetypes**, mirroring `Bot.archetype`: packaged goods · variants · serialized/high-value · prepared · services. A "product" means something genuinely different in a supermarket and a car dealership, and one generic form fails both.

### Feature flags — done and applied

Migration `019_commerce_feature_flags.sql`, applied and verified. **14 new keys: 8 in R1 (released), 6 in R2 (locked).** Registry now **63 features**, R1 holds 19.

**Deliberately free-tier.** Charging for the sensor would be backwards, and a till is the strongest acquisition hook Kola has.

**A two-layer model worth stating, because it is easy to confuse:** the flags control whether commerce is AVAILABLE on the platform; whether a given business has TURNED IT ON is a workspace setting. A released feature a business has not enabled is not the same as a locked one, and the dashboard must render them differently — *"you could turn this on"* versus not existing at all.

### What's actually built and released

`commerce.pos` (R1) is released and live, not just flagged. The sales counter (`till_page.dart`) is a real working till: cart with quantity/price editing, an "ask price" tile flow for open-priced items, a real camera-based barcode scanner (device camera, not a stub), and a persistent bottom nav with pull-to-refresh on mobile. A sale writes through to stock — `Product.quantity` decrements on sale and the dashboard reflects it without a manual refresh. Two document surfaces exist: an A4 invoice (real entity + endpoint + a real payment link, not a mockup) and an end-of-day report (aggregation endpoint + page). Mobile responsiveness across the commerce surfaces (till, catalog grid, invoice/report tables) was a separate, later pass and is done.

## Phase 12 — Event Bus & the Observation/Recommendation Engine (Layers 4–6) — Both built; entirely undocumented in this file until this correction (2026-08-31)

**Found while auditing Phase 9 for staleness.** Phase 9's own "What Layer 2 unlocked next" section predicted these as the natural next build and named them as future work. They were, in fact, built — under the internal names "Gate 2" (event bus/webhooks) and the "Observation Engine" (findings) — and neither ever got a Phase 12+ section here. This is the same class of gap the Connect Gate correction (Phase 8, section 8m) found: a real, shipped, multi-file subsystem invisible to anyone reading only this document.

### 12a. Event Bus (Layer 4) — Done

`EventBus.emit` (`kola_server/lib/src/services/connectors/contract/event_bus.dart`) is the single entry point every emission call site in the codebase goes through — no caller writes to the `events` table directly. Backed by `event.spy.yaml` + migration `037_event_bus.sql`. Two real design decisions worth recording:

- **`emit` never throws.** Same discipline as `ConnectorSyncLogRepository.record()` and the owner-notification dispatchers already in this codebase: a failure to record or fan out an event must never be the reason a real business action (an errand executing, a payment confirming) fails or rolls back. Every failure logs loudly instead.
- **Idempotent by `(workspaceId, fingerprint)`.** Two `emit` calls with the same fingerprint ('kind:subject', e.g. `'errand_executed:412'`) converge to one stored event and at most one webhook delivery round, regardless of how many times a retried handler or replayed sync actually calls it.

`WebhookDeliveryService` is the actual outbound half: on a genuinely new event, it fans out to every workspace webhook subscriber for that event type, HMAC-SHA256-signing the payload (`X-Kola-Signature`, hex-encoded) against the subscriber's own stored secret — a new signing scheme this codebase didn't have before, deliberately shaped like WhatsApp's existing inbound signature verification so one verification pattern serves both directions. This is what `api_webhooks_page.dart` (task #40, "Gate 8: Outbound messaging API" in this session's own history) surfaces to an owner as configurable webhook endpoints and event types — so the dashboard side of this was already tracked under a task number, just never connected back to "this is Layer 4 of the ten-layer architecture" in this document.

### 12b. Observation Engine / findings (Layer 5) — Done, deterministic by design

`WorkspaceSweepService` (`kola_server/lib/src/services/observation/`) replaces what used to be an inline, ad-hoc "Needs your attention" computed from whatever the Overview page had already fetched (so it could only ever mention escalated conversations and open tickets). It now runs real detectors — `FindingKinds`: out-of-stock/low-stock/missing-price/missing-photo products, escalated/waiting conversations, overdue/due-soon support tickets, failed documents, an empty knowledge base, no channel connected, an unmatched payment — over `WorkspaceFinding` rows (migration `034_workspace_findings.sql`).

**Deliberately deterministic, not model-generated.** Every detector is a rule over rows the workspace already has; no model is consulted and no wording is generated. The file's own header is explicit about why: "this product has 0 stock" is a fact, and the Overview is the worst screen in the product for a plausible-sounding mistake. A `confidence` field exists on each row precisely so a future AI-authored line (see 12c) can visibly read as less certain than a counted fact, instead of sitting beside it looking equally solid.

**The sweep is a reconciliation, not an insert.** Each run computes the finding set that *should* exist right now, then: present-and-stored → touch `last_seen_at`; present-and-not-stored → insert; stored-but-absent-now → mark resolved. That third case is what makes the list trustworthy — without it, restocking a product would leave a stale alert on screen until someone deleted it by hand.

**No scheduler yet, and that's a documented, deliberate choice, not an oversight.** `FindingEndpoint.listFindings` runs the sweep synchronously on every read rather than serving whatever a periodic job last computed — there is no `WorkspaceSweepService` entry in `server.dart`'s list of `Timer.periodic` sweeps (trial, support-ticket SLA, customer campaign, connector sync, broadcast all have one; this doesn't). The endpoint's own header explains the seam is already right for adding one later: it depends on the *service*, not on the timing, so wiring a scheduled pass later turns this into a plain read with zero interface change. A sweep costs a handful of indexed reads over one workspace — the same order of cost as the Overview's other calls — so serving-on-read today is a reasonable v1, not a shortcut that will need undoing.

`FindingEndpoint` (list + dismiss, both workspace-access-checked) is consumed by `overview_page.dart`'s findings list and its "Top recommendation" card (`_topRecommendation`, showing the single worst finding) — this is task #47 in this session's own history ("Investigate: Observations/Recommendations disappeared entirely from Overview"), confirming the feature was built, broke, and was fixed, all without ever being written up as the Layer 5/6 implementation it actually is.

### 12c. Recommendation Engine (Layer 6) — Partially built; the AI-reasoning layer is a deliberately unfilled seam, not a gap that was missed

The "Top recommendation" card on the Overview is real, but today it is just the worst `WorkspaceFinding` by severity — a deterministic fact, not a generated recommendation reasoning across multiple findings. `workspace_sweep_service.dart`'s own header names this directly: "three of your six low-stock items are Ankara; your supplier trip is overdue" is a different job from detection — it runs once per sweep rather than once per finding, and is deliberately not wired yet. The seam (the `confidence` field, the fact that detection is fully decoupled from any AI call) is designed in; filling it with an actual model call is the real remaining work here.

### Still not done (Layers 4–6, corrected scope)

- **Recommendation reasoning across findings** (12c) — the seam exists, nothing calls a model yet.
- **A scheduled sweep pass** (12b) — works correctly without one today; only matters once findings are read from somewhere other than the Overview's own on-demand load, or the per-read sweep cost becomes worth avoiding.
- **Timeline (Layer 8)** — still genuinely not built; see Phase 9's corrected "What Layer 2 unlocked next" note.
- **Continuous Learning (Layer 9)** — still genuinely not built; same conversation-to-memory promotion gap Phase 9 already names.
